### 1.1 Teste de restauração (gc-dev, 2026-10-26)

| Passo | Resultado |
|---|---|
| Dump do schema, `npx supabase db dump --linked` (21:55) | 163.656 bytes, 1 min 37 s (inclui o pull da imagem do `pg_dump`) |
| Dump dos dados, `--data-only --use-copy` (21:57) | 3.071.438 bytes, 17,7 s; traz `public`, `auth` e `storage` |
| Destino | container Docker descartável `public.ecr.aws/supabase/postgres:17.6.1.105`, a mesma versão do gc-dev, porta 54999 |
| Restauração com `psql`: `schema.sql`, depois `dados.sql` (21:58) | **schema 1 s + dados menos de 1 s: cerca de 2 s no total**, medido por relógio de parede em segundos inteiros. Schema: 0 erros |
| Contagem das 20 tabelas de `public`, gc-dev × restaurado | **20/20 iguais:** acordo_parcelas 10, acordos_pagamento 5, auditoria_eventos 2575, automacao_eventos 87, clientes 57, contatos_whatsapp 3, contratos 10, documentos_processamento 57, empresas 2, execucao 53, execucao_medicoes 19, fd 5, itens 76, notas_fiscais 8, obras 4, orcamentos 28, pagamentos 9, pedidos_acesso 0, profiles 8, propostas 17 |
| Container derrubado | `docker rm -f gc-restore-teste`; nenhum container sobrando |

O que o teste **achou** (vale para quem operar prod):

1. **Só `public` restaura limpo.** O dump de dados leva `auth` e `storage`, mas o schema deles é do
   Supabase, e o dump de schema não o recria. Os `COPY` de `auth` e `storage` falharam no destino
   (33 erros no log, todos desses dois schemas: colunas e tabelas de versão diferente, e tabelas
   inexistentes). `auth.users` ficou com 0 linhas no destino, contra 8 em gc-dev. Para recuperar
   usuários num incidente, o caminho é o *Restore* do painel ou o PITR (o mesmo projeto), ou
   recriar os usuários por convite; o dump lógico cobre as tabelas do sistema.
2. **As FKs de `profiles` para `auth.users` não bloquearam** porque o dump de dados liga
   `session_replication_role = replica`. Quem restaurar sem isso precisa da ordem `auth` antes.
3. **O Storage (anexos) não está em nenhum dump** e não foi baixado neste ensaio.
4. **Tempo de sistema parado:** a restauração de `public` leva segundos nesse volume (3 MB). O que
   pesa num incidente é o tempo de reativar o projeto e subir o Storage, não o `psql`. Em prod o
   volume deve ser maior, e o tempo deve ser medido de novo.

Os arquivos ficaram em `~/.claude/jobs/2a37dcc8/tmp/backup-gcdev/` (fora do repositório).
