008/009/010 entraram no último commit (`migration e documetacao`), depois da

## 2. Não há como saber o que está aplicado — só introspecção

Não existe `supabase/migrations/`, `supabase/config.toml`, nem projeto
linkado pela CLI. Os `.sql` são scripts numerados aplicados **à mão** no SQL
Editor. Consequências:

- não existe tabela de controle (`schema_migrations`) pra consultar;
- "rodar as migrations pendentes em gc-dev" não corresponde a nenhum comando;
- a única forma de conferir é **inspecionar o catálogo do Postgres**.

Foi escrito pra isso: **`supabase/verificar_schema_aplicado.sql`** —
somente leitura, seguro em prod. Rodar nos dois projetos e comparar:

```
SQL Editor do gc-dev  -> colar -> Run
SQL Editor do gc-prod -> colar -> Run
```

Cada linha sai como OK / FALTA, por migration: tabela `clientes`,
colunas legacy de `obras`/`orcamentos` dropadas, FK `obras_cliente_fk`,
4 views recriadas, RLS + policies de `clientes`, o CASO 2 da
`calcular_valores_obra` (006), a coluna `progresso_itens_pct` na view (007),
`documentos_processamento` (008), `contatos_whatsapp` (009), bucket +
policies de storage (010), e contagens totais de tabelas/policies pra
diff dev↔prod.

## 3. Ordem e idempotência: onde isso explode

| Migration | Idempotente? | Em transação? | Observação |
|---|---|---|---|
| 004 | **não** | sim (`begin`/`commit`) | `create table clientes` e `drop column` sem `if [not] exists`; migra dados de `obras` para `clientes` |
| 005 | sim | não | `drop policy if exists` antes de cada `create policy` |
| 006 | sim | n/a | `create or replace function` |
| 007 | sim | n/a | `create or replace view` |
| 008 | **não** | **não** | `create table documentos_processamento` sem guard |
| 009 | **não** | **não** | `create table contatos_whatsapp` sem guard |
| 010 | sim | não | `on conflict do nothing` + `drop policy if exists` |

Três armadilhas concretas:

1. **004 depois de 007 reverte o 007.** A 004 recria `obras_com_valores` no
   final (linha 536) *sem* `progresso_itens_pct`. A listagem de obras
   seleciona essa coluna explicitamente
   (`src/app/(app)/obras/page.tsx:51`) — a página quebra em runtime.
   Ordem obrigatória: **004 -> 005 -> 006 -> 007 -> 008 -> 009 -> 010**.
2. **004 sem 006 quebra a listagem inteira.** É o que o cabeçalho do 006
   diz: a 004 dropa os campos legacy que a `calcular_valores_obra`
   assumia, e a view chama a função via `LATERAL`. Aplicar 004 em prod e
   parar ali derruba `/obras`.
3. **008 e 009 não estão em transação.** Se falharem no meio (ex.: index ou
   policy), deixam estado parcial. Vale envolver em `begin; ... commit;`
   antes de aplicar em prod.

Sobre a 004 em prod: ela dropa 13 colunas de `obras`
(`cliente`, `contato`, `cpf_cnpj`, `telefone`, `email`, `valor_total`,
`desconto`, `valor_final`, `pct_*`, `forma_pagamento`, `doc_url`) e 6 de
`orcamentos`, depois de copiar os dados pra `clientes`. É irreversível sem
backup. O próprio arquivo pede janela de manutenção — o checklist da tarefa
("Aplicar as mesmas migrations em gc-prod") não menciona backup nem janela.

## 4. `types.ts` está desatualizado

`src/lib/supabase/types.ts` (2267 linhas) **não contém**:

- `progresso_itens_pct` em `obras_com_valores` (007)
- a tabela `documentos_processamento` (008)
- a tabela `contatos_whatsapp` (009)

Ou seja: foi gerado antes do commit e2dcc57 e antes do 007 chegar na view do
projeto de onde foi gerado.

Além disso, `package.json` fixa o projeto no script:

```json
"db:types": "npx --yes supabase gen types typescript --project-id gzbmhgnpoehormnidmgg > src/lib/supabase/types.ts"
```

O `--project-id` está hardcoded e o repositório não documenta se
`gzbmhgnpoehormnidmgg` é gc-dev ou gc-prod. Não existe forma de gerar types
do outro ambiente — que é justamente o que a tarefa pede pra comparar.
Sugestão: `db:types:dev` / `db:types:prod`, ou `--project-id $SUPABASE_PROJECT_ID`.

## 5. `tsc` e `lint` já passam — e não provam nada

Rodados agora, nesta branch, com os types velhos:

```
npx tsc --noEmit   -> sem erros
npm run lint       -> No ESLint warnings or errors
```

Os dois itens do checklist já estão verdes **apesar** do drift. Por quê:

- `src/lib/types.ts:232` declara `progresso_itens_pct` à mão;
- `src/app/(app)/obras/page.tsx:96` faz `(data ?? []) as unknown as ObraListItem[]`.

O `as unknown as` apaga qualquer divergência entre o `select(...)` e o
`Database` gerado. Enquanto esse cast existir, `tsc` nunca vai detectar
coluna faltando — nem agora, nem numa próxima migration. O critério de
aceite "npx tsc --noEmit passando sem erro" é, aqui, um teste que não
pode falhar.
