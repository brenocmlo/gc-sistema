## 2. Decisões

- **O banco continua sendo a regra.** A cascata são quatro CHECKs de coluna na tabela
  `execucao`. O status de cada etapa é GENERATED, e as datas de início, atualização e fim vêm do
  trigger `execucao_preenche_datas`. Os helpers só repetem a regra para a tela limitar o input
  e explicar o bloqueio antes do POST, e para a action recusar com mensagem legível. Nenhuma
  data nem status é gravado pela aplicação.
- **Comparação em milésimos**, e não com `<=` em ponto flutuante: `0,1 + 0,2` tem de ser igual
  a `0,3`, como no `numeric` do banco.
- **Progresso geral é a média das quatro etapas**, cada uma com o mesmo peso. A view
  `obras_com_valores` mede o progresso da obra só pela medição (`progresso_itens_pct`). As duas
  medidas respondem a perguntas diferentes, e o 7.2 mostra as quatro etapas separadas.

## 3. Achado para o 7.4: `quantidade_total` com várias execuções por item

A migration `20260511151924` (a "004") tirou o `unique(item_id)` e criou o `sequencial`, mas
os dois triggers de quantidade continuaram escritos para uma execução por item:

- `execucao_set_quantidade_total` (BEFORE INSERT) **sobrescreve** `quantidade_total` com a
  quantidade inteira do item, mesmo que o insert mande outra. Uma segunda execução do mesmo item
  nasce com o total do item, e não com a parte dela.
- `itens_sincroniza_execucao_qtd` (quando `itens.quantidade` muda) grava a quantidade do item
  em **todas** as execuções dele.
- Ao reduzir a quantidade de um item para menos do que uma execução já fabricou, o
  `fab_qtd <= quantidade_total` recusa. O update do item falha com o erro cru do CHECK.

Com isso, a atividade do 7.4 "soma das quantidades não ultrapassa a do item" não tem como ser
cumprida. **O 7.4 precisa de uma migration** que faça o insert respeitar o `quantidade_total`
enviado (e só usar a do item quando vier nulo) e que troque a sincronização por outra regra.
Proponho:

- com uma execução, a sincronização continua como hoje;
- com várias, a mudança de quantidade do item não reparte sozinha, e a tela pede para ajustar.

É decisão de modelagem, e fica para o início do 7.4. **Atualização:** resolvido no 7.4, com a migration `20260924110000_execucao_varias_por_item.sql`.
