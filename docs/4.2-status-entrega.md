# Bloco 4.2, Propostas: types, helpers e layout-guard — status de entrega

Data: 2026-09-03. Branch: feature-dev-breno-automacao. Commit: 1de7ea5.

## O que o bloco é

Preparar a base da entidade Propostas, sem tela: os tipos, os helpers puros e o
guard de perfil que as telas dos blocos seguintes vão consumir. O padrão seguido
é o de Orçamentos e FD — `src/lib/types.ts` para os aliases de tabela,
`src/lib/<entidade>.ts` para regra pura e `layout.tsx` com `requirePerfil`.

## Atividade 2: PropostaListItem com JOIN de obra e cliente

**Concluída, com uma correção de premissa.**

A tarefa pede "JOIN de obra (codigo_obra, nome) e cliente", o que sugere dois
JOINs irmãos, como em `OrcamentoListItem`. Não é possível: **propostas não tem
`cliente_id`**. A tabela liga em obra pela FK composta
`propostas_obra_fk (obra_id, empresa_id)`, e o cliente vem por obra. O JOIN é
aninhado, `propostas → obras → clientes`:

```ts
obra: (Pick<Obra, 'codigo_obra' | 'nome'> & {
  cliente: Pick<Cliente, 'nome'> | null
}) | null
```

O select correspondente, para as telas do próximo bloco:

```
id, numero, data_emissao, data_validade, obra_id, status,
valor_total, desconto, valor_final,
obra:obras(codigo_obra, nome, cliente:clientes(nome))
```

`valor_total`, `desconto` e `valor_final` entram juntos porque `valor_final` é
coluna **generated** (`valor_total - desconto`), e a listagem precisa mostrar o
desconto sem uma segunda consulta.

## Atividade 3: src/lib/propostas.ts

### Status

| Export | O que faz |
|---|---|
| `STATUS_PROPOSTA_LABELS`, `formatStatusPropostaLabel` | rótulos em português, mesmo formato do `fd.ts` |
| `STATUS_PROPOSTA_OPTIONS` | lista pronta para `<select>` e para o diálogo de status |
| `isPropostaStatus` | type guard para querystring (`?status=`) e input externo |
| `requiresDataEnvio`, `requiresDataDecisao`, `requiresMotivoRejeicao` | quais campos cada status exige |
| `isEditavel`, `isFinalizada` | rascunho é o único editável; aprovada e rejeitada são terminais |
| `PROPOSTA_TRANSICOES`, `canChangePropostaStatus` | fluxo permitido entre status |
| `isPropostaVencida` | validade expirada, derivada em runtime |
| `validarMotivoRejeicao` | espelha o CHECK `propostas_rejeitada_motivo` |

Duas decisões que valem registro, porque não vêm do banco:

**O fluxo de status é regra de aplicação.** O CHECK do banco valida só a lista de
valores (`rascunho`, `enviada`, `aprovada`, `rejeitada`), não a ordem. O que ficou
codificado é `rascunho → enviada`, `enviada → aprovada | rejeitada | rascunho`
(voltar para correção) e aprovada/rejeitada terminais. Se o fluxo comercial real
permitir reabrir uma decisão, é uma linha em `PROPOSTA_TRANSICOES`.

**Proposta vencida não é status.** Diferente de orçamento, que tem `expirado` no
banco, aqui não existe `expirada`. `isPropostaVencida` compara `data_validade`
com hoje e só vale para proposta `enviada` e ainda sem decisão — mesmo padrão do
`computeStatusFd` em `fd.ts`, que também deriva em runtime.

### Percentuais de pagamento

O ponto que mais exigia cuidado. No banco os quatro `pct_*` são
`numeric(5,4)` com `CHECK between 0 and 1`, ou seja **frações**, e existe o
`CHECK propostas_pct_soma` garantindo que a soma dos `coalesce(pct_*, 0)` não
passe de `1.0`. A UI trabalha em 0 a 100.

| Export | O que faz |
|---|---|
| `PCT_FIELDS`, `PctField`, `PCT_LABELS`, `PctValues` | os quatro campos, rótulos e o shape parcial |
| `somaPct`, `pctRestante`, `isPctCompleto` | soma com `coalesce`, o que sobra e se fecha 100% |
| `validarSomaPct` | espelha os dois CHECKs e devolve `soma` e `restante` |
| `pctToFraction`, `fractionToPct`, `formatPct` | conversão nas bordas e "12,5%" em pt-BR |
| `valorBaseProposta`, `valorParcela`, `parcelasDaProposta` | rateio em reais sobre o valor final |

Três detalhes deliberados:

1. **Arredondamento em 4 casas antes de comparar.** `numeric(5,4)` só guarda
   quatro decimais, e `0.1 + 0.2` em float dá `0.30000000000000004`. Sem o
   `round4`, uma soma legítima de 100% seria recusada pelo validador na frente
   de um banco que a aceitaria.
2. **Soma abaixo de 100% é válida.** O CHECK é `<= 1.0`, não `= 1.0`. O resto
   fica para o campo livre `condicoes_pagamento`, então `validarSomaPct` devolve
   `restante` em vez de barrar, e `isPctCompleto` existe para a tela sinalizar
   sem bloquear o salvamento.
3. **A base de rateio é `valor_final`.** É generated no banco;
   `valorBaseProposta` tem fallback para `valor_total - desconto` só para o caso
   do registro em memória que ainda não voltou do insert.

## Verificação

| Comando | Resultado |

| `npx tsc --noEmit` | limpo |
| `npm run lint` | sem warnings nem erros |

O repositório passou a ter teste automatizado, sem dependência nova: o Node 24
executa `.ts` direto por type stripping nativo, então `node --test` basta. Por
isso o import no teste traz a extensão (`./propostas.ts`) — o Node não resolve
extensão nem o alias `@/` — e o `tsconfig.json` ganhou
`allowImportingTsExtensions`, que só é aceito porque o projeto já é `noEmit`.

Os 17 casos cobrem `src/lib/propostas.ts` inteiro: os guards e transições de
status, `isPropostaVencida`, `validarMotivoRejeicao`, os dois CHECKs de `pct_*`,
a conversão de borda entre UI e banco e o rateio em reais. Dois merecem
destaque, porque travam regressão em cima de decisão sutil: a soma
`0.1 + 0.2 + 0.3 + 0.4` precisa ser aceita como 100% (sem o `round4` o float
recusaria), e a soma das parcelas mais o restante precisa fechar exatamente o
valor final.

## O que vem depois

O bloco 4.2 entrega base, não tela. `src/app/(app)/propostas/page.tsx` continua
em `<EmConstrucao />`. Seguindo o que Orçamentos já tem, é isto que falta para
Propostas ficar completa:

1. **Listagem.** `page.tsx` com o select da atividade 2, mais `filters.tsx` e
   `propostas-table.tsx`. Lição do 4.1 que se aplica aqui: usar `as` e nunca
   `as unknown as` no retorno do `select()`, senão o compilador para de comparar
   a string da query com o `Database` gerado e o `tsc` deixa de acusar coluna
   inexistente.
2. **Criação e edição.** `proposta-form-helpers.ts` com schema zod e o par
   `formValuesToPayload` / `propostaToFormValues`, mais `proposta-form.tsx`. É
   onde `pctToFraction` e `fractionToPct` entram: o form em 0 a 100, o payload em
   fração. O schema precisa reproduzir `desconto <= valor_total`
   (CHECK `propostas_desconto_valido`) e chamar `validarSomaPct` antes de
   submeter. A seleção de obra substitui a de cliente de orçamentos, e o `numero`
   é obrigatório em proposta, diferente de orçamento.
3. **Detalhe e mudança de status.** `[id]/page.tsx`, `detail-header.tsx` e
   `status-dialog.tsx` sobre `canChangePropostaStatus`, `requiresDataEnvio`,
   `requiresDataDecisao` e `validarMotivoRejeicao`. O diálogo precisa limpar
   `motivo_rejeicao` e `detalhe_rejeicao` quando o status sai de `rejeitada`,
   porque o CHECK do banco proíbe motivo em status diferente de rejeitada, igual
   ao que `changeOrcamentoStatus` já faz. O diálogo também não oferece
   destino nenhum para proposta aprovada ou rejeitada, conforme a pendência 2.
4. **Anexos.** `anexos-tab.tsx` sobre a coluna `anexos` jsonb e o bucket
   `anexos`, reusando `buildStoragePath`, `validateFile` e o tipo `Anexo`.
5. **Permissão de escrita nas Server Actions.** O guard de layout protege a
   rota, não a ação. As actions precisam repetir o padrão de orçamentos: admin e
   comercial mudam status e editam, só admin exclui. E vale lembrar que
   `propostas_obra_fk` é `ON DELETE RESTRICT`, então obra com proposta não é
   deletável — o erro do banco tem que virar mensagem legível.
6. **Exportação.** `api/export/propostas`, no formato dos três que já existem.
7. **Painel financeiro da proposta**, se entrar no escopo: a view
   `propostas_financeiro` já existe e traz `total_nfs`, `recebido_nfs`,
   `total_acordos` e `recebido_acordos`, e o alias `PropostaFinanceiro` já está
   em `types.ts`.

   selo âmbar ao lado do `StatusBadge` quando `isPropostaVencida` for verdadeiro,
   e uma opção "Vencidas" no `filters.tsx`; no detalhe, o mesmo selo no
   `detail-header.tsx`. Como vencida não é status do banco, o filtro não vira
   `eq('status', ...)`: a query filtra `status = 'enviada'` com
   `data_validade < hoje`, e a querystring usa uma chave própria (`?vencidas=1`)
   para não colidir com o `?status=` que `isPropostaStatus` valida.
4. **Herdada do 4.1, ainda aberta:** `supabase migration repair --status applied`
   nas dez versões antes de qualquer `db push`. Depende de personal access token
   e `supabase link`. Junto dela seguem a revogação do token antigo, usado para
   gerar os types, e gc-prod quando despausar.
