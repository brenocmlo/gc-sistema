## 2. As duas falhas de segurança corrigidas

Ambas foram provadas em gc-dev em 2026-10-05, numa transação desfeita no fim, antes da correção.

**1. Qualquer usuário virava admin pela API do Supabase.** A policy "Usuário edita próprio
perfil" (desde a migration inicial) deixava o usuário atualizar a própria linha conferindo só o
`id` e a empresa, sem travar nenhuma coluna. Com a sessão do comercial, `update profiles set perfil
= 'admin' where id = auth.uid()` passava, e `has_perfil(array['admin'])` respondia verdadeiro.
- **Correção:** o trigger `profiles_proteger` (BEFORE UPDATE OR DELETE) deixa só o admin mudar
  perfil, situação e e-mail, e ninguém muda a empresa de um usuário.
- **A mesma trava protege a operação:** a empresa nunca fica sem admin ativo. Rebaixar, desativar
  ou excluir o último admin é recusado.

**2. Usuário desativado continuava lendo e gravando.** As funções `current_empresa_id()`,
`current_perfil()` e `has_perfil()`, que todas as policies usam, não olhavam `profiles.ativo`.
- **Correção:** as três passam a exigir o usuário ativo, e o inativo não passa em nenhuma policy.
- **Uma policy nova** deixa todo usuário ler a **própria** linha, para a aplicação conseguir dizer
  "acesso desativado".

**Provas depois da migration**, também em transação desfeita:

| Caso | Resultado |
|---|---|
| Comercial muda o próprio perfil para admin | **recusado**: "Só o admin muda o perfil, a situação ou o e-mail de um usuário" |
| Comercial muda o próprio nome | permitido |
| Admin muda o perfil do comercial | permitido |
| Comercial desativado: `current_empresa_id()` | nulo |
| Comercial desativado: obras visíveis | 0 |
| Comercial desativado: a própria linha | 1 (lê) |
| Rebaixar os 2 admins ativos da empresa | **recusado**: "A empresa precisa de ao menos um admin ativo" |

As mesmas regras ficaram permanentes na camada escrita (seção 4).

**Registro para quem for operar gc-prod:** a migration `20261005120000` corrige falhas que também
existem em gc-prod (as policies vêm da migration inicial). Ela precisa ir junto com as pendentes de
prod, e antes do go-live (sprint 14). A gestão de usuários precisa de `SUPABASE_SERVICE_ROLE_KEY`
no ambiente do servidor; sem ela, a tela avisa e não convida.

## 3. Achado para o 13.3

O **cadastro aberto** está ligado no Auth do gc-dev (`disable_signup = false`). Qualquer um com a
chave pública consegue criar conta pela API. Sem perfil, essa conta não lê nada (as funções das
policies devolvem nulo), mas a conta existe. Desligar o cadastro é decisão de configuração do
projeto e entra na revisão de RLS e segurança do 13.3.

## 5. Pendências

  exemplo), o mesmo convite pode também mandar o e-mail.
- **Validade do link**: 1 hora no gc-dev. Para o uso real, vale avaliar 24 horas
  (`mailer_otp_exp`), que é configuração do projeto.
