A 004 é destrutiva, não idempotente e sensível à ordem

A 004_revisao_schema.sql cria a tabela clientes, migra os dados de cliente que moravam em obras, e então dropa as colunas antigas — sem if not exists na criação e sem if exists nos drops. Ela está envolvida em begin/commit, então uma segunda execução aborta inteira em vez de deixar meio caminho. O risco não é re-rodar: é rodar a primeira vez em produção.

2

O escopo real é 004–010

Três migrations entraram no último commit (e2dcc57 — migration e documetacao), depois da tarefa ter sido criada: 

supabase/004_revisao_schema.sql
supabase/005_rls_clientes.sql
supabase/006_fix_calcular_valores_obra.sql
supabase/007_progresso_itens_obra.sql
supabase/008_documentos_processamento.sql                  ← e2dcc57
supabase/009_contatos_whatsapp.sql                         ← e2dcc57
supabase/010_storage_bucket_documentos_processamento.sql   ← e2dcc57

A 010 é a mais fácil de esquecer e a mais barulhenta quando falta: ela cria o bucket documentos-processamento e as policies de storage.objects que exigem o empresa_id como primeiro segmento do path. O workflow n8n de ingestão via WhatsApp já grava em {empresa_id}/whatsapp/{messageId}-{fileName} contando com isso. Se a 010 não estiver em prod, a ingestão falha em prod — e nenhum item do checklist original detecta, porque storage não aparece nos types nem no compilador.

3

Ninguém sabe o que já rodou — e não é descuido, é ausência de mecanismo

Não existe supabase/migrations/, não existe supabase/config.toml, não existe projeto linkado pela CLI. Os .sql são scripts numerados aplicados à mão no SQL Editor. Daí decorrem três coisas:

  • não há tabela de controle (schema_migrations) pra consultar;
  • "rodar as migrations pendentes em gc-dev" não corresponde a comando nenhum;
  • a única forma de conferir é inspecionar o catálogo do Postgres.

Foi pra isso que escrevi supabase/verificar_schema_aplicado.sql: somente leitura, seguro pra rodar em produção. Cola no SQL Editor de cada projeto e sai uma linha ok ou falta por evidência — tabela clientes, colunas legacy dropadas, FK obras_cliente_fk, as 4 views recriadas, RLS e contagem de policies, o CASO 2 da calcular_valores_obra, a coluna progresso_itens_pct, as duas tabelas novas, o bucket e suas policies — mais contagens totais de tabelas e policies pra diff direto entre dev e prod.

4

Os critérios de aceite não podem falhar

Rodados nesta branch, agora, com os types desatualizados:

$ npx tsc --noEmit
(sem erros)

$ npm run lint
✓ No ESLint warnings or errors

Os itens 4 e 5 do checklist já estão verdes apesar do drift, por dois motivos concretos: src/lib/types.ts:232 declara progresso_itens_pct à mão, e src/app/(app)/obras/page.tsx:96 faz (data ?? []) as unknown as ObraListItem[]. O as unknown as apaga qualquer divergência entre a string do select() e o Database gerado. Enquanto ele existir, o tsc nunca vai apontar coluna faltando — nem agora, nem na próxima migration.

5

O drift de types, objeto por objeto

src/lib/supabase/types.ts tem 2.267 linhas e não contém nenhum destes três:

Migration 007 obras_com_valores.progresso_itens_pct ausente da view tipada
Migration 008 documentos_processamento tabela ausente
Migration 009 contatos_whatsapp tabela ausente

E o script de geração aponta pra um projeto fixo, sem chave de ambiente: 

// package.json
"db:types": "npx --yes supabase gen types typescript
              --project-id gzbmhgnpoehormnidmgg > src/lib/supabase/types.ts"

O repositório não documenta se gzbmhgnpoehormnidmgg é gc-dev ou gc-prod, e não há como gerar os types do outro ambiente — que é exatamente o que a tarefa pede pra comparar. Caminho: dois scripts (db:types:dev / db:types:prod) ou --project-id $SUPABASE_PROJECT_ID.

Checklist corrigido

  1. 01Rodar supabase/verificar_schema_aplicado.sql em gc-dev e salvar a saída
  2. 02Rodar o mesmo em gc-prod e salvar a saída
  3. 03Diffar as duas saídas — essa é a lista real de pendências por ambiente

Preparação passos 4–5

  1. 04Confirmar qual projeto é gzbmhgnpoehormnidmgg e ajustar db:types pra alcançar os dois
  2. 05Envolver 008 e 009 em begin; … commit;

  1. 06Aplicar o que falta em gc-dev, na ordem 004→010, e revalidar com o script
  2. 07Backup + janela de manutenção antes de qualquer coisa em gc-prod — a 004 é irreversível
  3. 08Aplicar em gc-prod na mesma ordem e revalidar com o script

  1. 09npm run db:types e conferir no diff que os três objetos ausentes apareceram
