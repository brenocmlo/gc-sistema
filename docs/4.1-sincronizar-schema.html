A 010 é a mais fácil de esquecer e a mais barulhenta quando falta: ela cria o bucket documentos-processamento e as policies de storage.objects que exigem o empresa_id como primeiro segmento do path. O workflow n8n de ingestão via WhatsApp já grava em {empresa_id}/whatsapp/{messageId}-{fileName} contando com isso. A verificação confirmou a 010 aplicada em dev, então a ingestão está de pé no ambiente em uso; em prod é pendência registrada — e do tipo que nenhum item do checklist original detectaria, porque storage não aparece nos types nem no compilador.

3

Ninguém sabe o que já rodou — e não é descuido, é ausência de mecanismo

Não existe supabase/migrations/, não existe supabase/config.toml, não existe projeto linkado pela CLI. Os .sql são scripts numerados aplicados à mão no SQL Editor. Daí decorrem três coisas:

  • não há tabela de controle (schema_migrations) pra consultar;
  • "rodar as migrations pendentes em gc-dev" não corresponde a comando nenhum;
  • a única forma de conferir é inspecionar o catálogo do Postgres.

Foi pra isso que escrevi supabase/verificar_schema_aplicado.sql: somente leitura, seguro pra rodar em produção. Cola no SQL Editor de cada projeto e sai uma linha ok ou falta por evidência — tabela clientes, colunas legacy dropadas, FK obras_cliente_fk, as 4 views recriadas, RLS e contagem de policies, o CASO 2 da calcular_valores_obra, a coluna progresso_itens_pct, as duas tabelas novas, o bucket e suas policies — mais contagens totais de tabelas e policies pra diff direto entre dev e prod.

Os itens 4 e 5 do checklist já estão verdes apesar do drift, por dois motivos concretos: src/lib/types.ts:232 declara progresso_itens_pct à mão, e src/app/(app)/obras/page.tsx:96 faz (data ?? Enquanto ele existir, o tsc nunca vai apontar coluna faltando — nem agora, nem na próxima migration.

5

O drift de types, objeto por objeto

src/lib/supabase/types.ts tem 2.267 linhas e não contém nenhum destes três:

Migration 007 obras_com_valores.progresso_itens_pct ausente da view tipada
Migration 008 documentos_processamento tabela ausente
Migration 009 contatos_whatsapp tabela ausente

E o script de geração aponta pra um projeto fixo, sem chave de ambiente: 

// package.json — como estava
"db:types": "npx --yes supabase gen types typescript
              --project-id gzbmhgnpoehormnidmgg > src/lib/supabase/types.ts"

// como está agora: gera num .tmp e só promove se der certo
"db:types": "npx --yes supabase gen types typescript
              --project-id ${SUPABASE_PROJECT_ID:-gzbmhgnpoehormnidmgg}
              > src/lib/supabase/types.ts.tmp
              && mv src/lib/supabase/types.ts.tmp src/lib/supabase/types.ts
              || (rm -f src/lib/supabase/types.ts.tmp; exit 1)"

O repositório não documenta se gzbmhgnpoehormnidmgg é gc-dev ou gc-prod, e não há como gerar os types do outro ambiente. Caminho: dois scripts (db:types:dev / db:types:prod) ou --project-id $SUPABASE_PROJECT_ID.

Cuidado, e já mordeu: o script redirecionava com > direto pro arquivo final, e o shell trunca o destino antes de rodar o comando. Na primeira tentativa a CLI abortou por falta de token (supabase login) e o src/lib/supabase/types.ts ficou com 0 bytes — restaurado do commit e2dcc57 (blob ab59e07, 2267 linhas). O script agora escreve num .tmp e só promove com mv se a geração terminar bem, então uma falha deixa o arquivo bom intacto.

Com dev verificado, rodar npm run db:types agora responde essa pergunta de graça: se os três objetos ausentes aparecerem no diff, o id é gc-dev e o atraso era só falta de regenerar. Se não aparecerem — ou o comando falhar por projeto indisponível — o id aponta pra gc-prod, que está pausado, e o script precisa mudar antes de qualquer outra coisa.

Migrations sob a CLI

Os dez scripts numerados viraram um histórico que a CLI entende. Os timestamps são as datas reais dos commits que introduziram cada arquivo, então a ordem cronológica é idêntica à da numeração antiga — e a numeração ficou anotada no supabase/README.md, porque a documentação e as tarefas do ClickUp falam nesses números.

Falta um comando, e ele importa. As dez já estão aplicadas em dev, mas o histórico remoto da CLI está vazio — ela não tem como saber. Antes de qualquer db push, é preciso rodar migration repair --status applied nas dez versões; senão a CLI tenta reaplicar tudo a partir da revisao_schema, que é destrutiva. Ela aborta sozinha (está em begin/commit) e nada é perdido, mas o susto é evitável. Os comandos exatos estão em supabase/README.md.
